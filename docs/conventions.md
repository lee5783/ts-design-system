# Coding conventions

**Analysis date:** 2026-10-16

These rules are binding for library, demo and tooling code. Root `CLAUDE.md` adds the team rules: no new code comments, match the closest sibling file, no unit tests unless asked. Component contracts (per-toolkit API, matrix, accessibility) live in `design/specs/components/<name>.md`; this page holds the rules that apply across components.

## Naming patterns

### Types (C-29, no exceptions on either platform)

| Toolkit | Pattern | Examples |
|---|---|---|
| SwiftUI | `TS<Name>`, modifiers `.ts<Name>(…)` | `TSButton`, `TSIcon`, `TSBottomNavShell`, `.tsDialog(…)`, `.tsToastHost()` |
| UIKit | `TS<Name>View`, or the UIKit role suffix | `TSButtonView`, `TSIconView`, `TSDialogViewController`, `TSListItemCell`, `TSTabBarController`, `TSToastWindow` |
| Compose | `TS<Name>` composables | `TSButton`, `TSIcon`, `TSDialog`, `TSToastHost`, `TSTheme` |
| Views | `TS<Name>View`, or the Android role suffix | `TSButtonView`, `TSDialogFragment`, `TSBottomSheetDialogFragment`, `TSToastHost`, `TSListDecoration` |
| Shared layer | `TS<Name>StyleSpec`, `TS<Name>Accessibility`, `TS<Name>Action` | `TSCardStyleSpec`, `TSToastAccessibility`, `TSDialogAction` |

A SwiftUI `TSButton` and a UIKit `TSButtonView` never clash in one app. Android toasts are `TSToast` / `TSToastView`, never `Toast`.

### Tokens (generated, `tools/codegen/src/transforms/naming.ts`)

| DS token | iOS | Compose | Views / XML |
|---|---|---|---|
| `accent-primary` | `TSColor.accentPrimary`, `UIColor.tsAccentPrimary`, `Color.tsAccentPrimary` (`.tsAccentPrimary` in a `ShapeStyle` position) | `TSTheme.colors.accentPrimary` | `?attr/tsColorAccentPrimary`, `@color/ts_accent_primary` |
| `space-0-5` | `TSSpacing.space0_5` | `TSSpacing.space0_5` | `@dimen/ts_space_0_5` |
| `radius-xs` | `TSRadius.radiusXs` | `TSShapes.radiusXs` | `@dimen/ts_radius_xs` |
| icon `arrow-left` | `TSIconName.arrowLeft` | `TSIcon.ArrowLeft` (`:core`) | `@drawable/ts_ic_arrow_left` |
| logo | `Logos.xcassets` | — | `@drawable/ts_logo_*` |

- Every token family has an `allTokens` catalog (iOS) for demos and tests.
- Colours are `#AARRGGBB` in Android XML (the DS ships `#RRGGBBAA`).
- **Family-name repetition is intended (C-43):** `TSRadius.radiusXs` and `TSSpacing.space4` repeat the family name because they mirror the DS token names (`radius-xs`, `space-4`). Keep it; do not shorten to `TSRadius.xs`.
- Renamed tokens keep a generated deprecated alias (see [guides/deprecation-policy.md](guides/deprecation-policy.md)).
- Radius values ≥ 9999 are a **capsule**: iOS clamps them to half the height (`Capsule` / `cornerStyle .capsule`), Android to a fully rounded shape.

### Android resources

- `resourcePrefix = "ts_"` is enforced by `ds.android.library` (`DsBuildConstants.RESOURCE_PREFIX`). Attributes are `ts<Name>` (`tsVariant`, `tsTitle`); component-specific enum attrs are `ts<Name>Tone` (`tsAlertTone`, `tsBadgeTone`, `tsToastTone`) or `ts<Name>Variant` (`tsTabsVariant`). `tsVariant` is the one shared enum attr.
- **Exceptions to `resourcePrefix` (C-43):** the dotted style names `Base.Theme.TS`, `Base.ThemeOverlay.TS` and `MaterialAlertDialog.TS`, plus the other `Theme.TS*`, `ThemeOverlay.TS*`, `Widget.TS.*`, `TextAppearance.TS.*`, `ShapeAppearance.TS.*` and `Animation.TS.*` styles. Android style names follow the platform's dotted parent convention, which lint's prefix check does not model. The files that hold them declare `tools:ignore="ResourceName"` (`android/views/src/main/res/values/ts_themes.xml`, `ts_component_attrs.xml`, `ts_component_styles.xml`). New styles follow the same dotted pattern; new non-style resources take the `ts_` prefix.
- Weight-600 text appearances are split by qualifier: `values/` uses `sans-serif-medium` (API 26–27), `values-v28/` uses `android:textFontWeight`. Prefer resource qualifiers over `SDK_INT` checks in Views.

### Generated files

Generated files start with `Generated by tools/codegen from … Do not edit.` That header is the one comment the generator writes; the no-comments rule does not apply to it. Edit the generator, never the output, then run `make codegen`.

### Files and folders

- One folder per component in each toolkit: `Components/<Name>/` (iOS) and `components/<name>/` (Android, lowercase; `switchcontrol` because `switch` is a keyword). Cross-component helpers go in `Components/Shared/` / `components/shared/`.
- Compose keeps internal test hooks in one file per module: `android/compose/src/main/kotlin/com/ts/ds/compose/components/shared/TSInternalTesting.kt`.
- Non-source files (docs, specs, scripts' outputs) are kebab-case.

## Code style

- **Swift:** Swift 6 language mode (`swiftLanguageModes: [.v6]`), 4-space indent, `@MainActor` on UI types and queues. No SwiftLint; the sibling file is the style guide.
- **Kotlin:** official code style (`kotlin.code.style=official`), **explicit API mode** in every library module, JVM target 17.
- **TypeScript (`tools/`):** ESM, `tsc --noEmit` type-check in `make tools-test`, 2-space indent.
- **Formatting:** `.editorconfig` (LF, final newline, 4 spaces; 2 for JSON/YAML/TS/MD; tabs in the Makefile).
- **Lint:** Android lint with `NewApi` as an error and `abortOnError`, plus Slack's Compose lint rules (`compose-lints`), run by `make android-build`. Workflows are linted by `make actionlint`.

## Component pattern

Every component follows the T21 pattern on both platforms:

1. **Style spec** in the shared layer: a `Configuration` (variant, size, flags, `TSControlState`), `resolve` returning a `Resolved` of **roles** (`TSColorRole`, `TSTypeRole`, `TSShadowRole` on Android; token references on iOS), and `allConfigurations` for exhaustive spec tests.
2. **State:** `TSControlState.make(isPressed:isEnabled:isLoading:isFocused:)` on iOS; `TSControlState` on Android. Snapshot tests force a state with `forcingState(_:)` (SwiftUI) or `LocalTSForcedControlState` (Compose).
3. **Toolkit views** read only the spec, never raw tokens for stateful values.
4. **Accessibility text** comes from `TS<Name>Accessibility` in the shared layer, so all four toolkits read the same words.
5. **Tests:** spec tests once, then behaviour and snapshot tests per toolkit, then the demo pages ([guides/adding-a-component.md](guides/adding-a-component.md)).

Toolkit details that recur:

- Interactive SwiftUI controls are a `Button` with a `ButtonStyle`; toggles are `Button` + `ButtonStyle`, never `Toggle`.
- UIKit controls are `UIControl` subclasses; compound inputs (text field) are a `UIControl` that forwards editing events and its `accessibilityIdentifier` to the inner input. Non-interactive components are a plain `UIView` with one accessibility element.
- UIKit stroke borders are drawn on the layer (`layer.borderWidth`), not as a background stroke. UIKit cards carry the shadow on the outer layer and clip on an inner surface view. Set `insetsLayoutMarginsFromSafeArea = false` on any layout-margin stack inside a component.
- In UIKit `traitCollectionDidChange`, pass the parent's traits to child styling; child traits are stale there.
- Views components extend a platform layout (`LinearLayout`, `FrameLayout`), read `app:ts*` attrs and `android:enabled` from the styleable, and expose the same properties in Kotlin.
- Views use resource-qualified text appearances (`TextAppearance.TS.*`, `TextAppearance.TS.Component.*` for off-scale weights) instead of runtime `SDK_INT` checks.
- Compose fonts that need weight 600 use `withDsFontWeight(600)`; Compose fixed-chrome text (badges, bottom-nav labels) uses a clamped `Density` and `Dp.toSp()`, Views uses px sizes from `labelFontScale`.
- Never let an infinite animation run in a snapshot or Robolectric test: Robolectric `idle()` never returns while a Compose infinite transition runs.

## Interaction and accessibility rules

- **Touch targets:** 44 pt on iOS (`TSHitArea`, SwiftUI `tsMinimumHitArea(outset:edges:)`); 48 dp on Android (Compose `tsMinimumTouchTarget`, Views `TSTouchDelegateGroup`, which reports `TouchDelegateInfo` to accessibility and replaces any touch delegate already set on the parent). The visual size stays the DS size.
- **Pressed:** a flat pressed fill (`surface-pressed` or the variant's pressed token); ripple only when `TSTheme(rippleEnabled = true)`. A row or card shows a pressed state only when it has an action.
- **Focus ring:** SwiftUI `tsFocusRing`, UIKit `UIFocusHaloEffect` (`TSFocusRing`), Compose `tsFocusRing`. Views draw the ring outside the bounds when the parent leaves room and inside the shape for full-bleed shapes.
- **Toggles** (Checkbox, Switch, switch rows): one element with one trait and one value ("on/off", "checked/unchecked"), never `.selected`; the toggle trait comes through `TSAccessibilityTraitsCompat`. Listeners fire on user toggles only, not on programmatic changes. Haptics go through `DsHaptics.toggleEvent(checked)` on Android.
- **Tabs:** value "Tab, n of N", the selected trait, no button trait, no `.tabBar` container. Compose exposes "n of N" as the state description.
- **List rows and cards that are interactive** are one element; footer buttons and accessory actions become accessibility custom actions (order: footer, accessory, consumer `accessibilityActions`). The switch row is one toggle element: Compose `clearAndSetSemantics` with the track as the only toggleable, Views a `TouchDelegate` inside the row.
- **Card label and value:** the label is "title, subtitle"; when there is no title or subtitle the body text is the label. With a heading, the body becomes the value (iOS `accessibilityValue`, Android `stateDescription`).
- **Announcements are opt-in** (`announcesOnAppear` in SwiftUI, `announcesWhenShown` in UIKit, Compose and Views) for alerts; text-field errors use a live region; toasts announce once per id.
- **Text direction:** user text uses content direction aligned to the layout start (Compose `TextDirection.Content` / `withContentDirectionAtLayoutStart`; UIKit labels set explicit natural or leading alignment). A UIKit `UILabel` with an attributed `TSFont` string sets its own line-break mode in the paragraph style. UIKit text views use TextKit 1 for exact DS line heights.
- **Reduce motion:** iOS `TSReduceMotion`; Android `TSReduceMotion` (`:core/motion`), surfaced in Compose as `LocalTSReduceMotion`.
- **Large Content Viewer** (iOS bottom nav) appears only at system accessibility sizes, not under trait overrides.

## Presentation rules

- **Dialogs:** present UIKit dialogs through `TSDialogViewController.present(from:)` and Views dialogs through `present(manager, tag)` (`show` routes there). Both return `false` when refused; SwiftUI and Compose call `onRefused`. Handlers run after dismissal, so an action may open the next dialog. Escape closes a dialog (UIKit key command, SwiftUI `.keyboardShortcut(.cancelAction)`). Views and Compose dialog windows must re-provide `LocalDensity`; the Views dismissal callback is `onUserDismiss` because `DialogFragment.onDismiss` is taken.
- **Toasts:** install one host per scene (SwiftUI `.tsToastHost()` at the root, UIKit `TSToastWindow` in the scene delegate) or per Activity (Compose `TSToastHost { }` at the root, Views `TSToastHost.install(activity)`). Show through `TSToastQueue`, `LocalTSToastState` or `TSToastHost.from(context)`. UIKit consumers forward trait overrides with `applyTraits(from:)`. Inside a `TSDialogFragment().apply { }` block, resolve strings before the block (the fragment's own `getString` shadows the outer one).
- **Views list rows** need stable view ids so switch state survives a recreate.

## Error handling

- Tooling throws `Error`s with actionable messages and exits non-zero; Make targets print the next step (for example "skipping iOS 15.5: no available iPhone simulator for that runtime; create one or set IOS_OLDEST_DEVICE").
- Library code does not log in release builds. `TSDialogPresenter.begin` writes an `os.Logger` debug line in DEBUG builds when it refuses.

## Compat code

- Every `#available` check lives in `ios/Sources/TSFoundation/Compat/`, as `package` API, behind a `TSCompat` path that tests can inject (`path:` parameters). Component code never branches on the OS itself.
- Android newer-API calls go through `ViewCompat` / AndroidX helpers or a helper with an `sdkInt` parameter (`DsHaptics.constantFor`, `DsFontWeights.resolve`). `NewApi` lint is an error.

## Assets

- Icons are baked-stroke vectors (the DS `strokeWidth` prop is dropped). SVG input passes an attribute allowlist in `tools/codegen/src/icons/svg-source.ts`; `ds-sync` rejects scripts, `foreignObject`, event handlers, external references and DOCTYPE/ENTITY.
- Directional icons set `mirrorsInRTL: true` in `design/assets/icons/icons.meta.json`; codegen turns that into asset-catalog mirroring and `android:autoMirrored`.
- The wordmark has light and dark variants (`ts-wordmark-light.svg`, `ts-wordmark-dark.svg`).

## Demo apps

- **Boundaries** (`tools/demos/src/check-boundaries.ts`, run by `make demos-check-boundaries`):
  - `ios-swiftui` imports only `SwiftUI`, `Foundation`, `Combine`, `TSDesignSystem`, `TSDemoSupport`; `ios-uikit` the same with `UIKit` and `TSDesignSystemUIKit`. UI tests import only `XCTest` and `Foundation`.
  - No `@testable`, no `@_spi`, no remote Swift package; local package references only to `../..` and `../ios-demo-support`.
  - Android demos declare only the BOM and their toolkit artifact (`com.ts.ds:compose` or `com.ts.ds:views`) plus demo support; never `com.ts.ds:core`, `:tokens` or `:test-support`, never a project-path dependency into `android/`. The Views demo has no Compose at all.
  - Demo-support modules depend on nothing from the library and stay toolkit-agnostic.
- **Catalog check** (`tools/demos/src/check-catalog.ts`): every `design/specs/components/*.md` spec has a page id in both `DemoCatalog`s and a page file in all four apps (`icon` maps to the Icons foundation page).
- **Page patterns:** SwiftUI pages compose `DemoComponentSection`s; UIKit pages are `DemoPageViewController` subclasses; Compose pages use `DemoComponentSection`; Views pages use `DemoPageFragment` with `DemoPageState`, `DemoChoiceGroup` and `DemoTapCounter`. Page dialogs need distinct tags and a `representDialog` mapping so they re-present after a recreate. Views demo ids come from `res/values/ids.xml` (`demo_stable_ids`).
- **Settings** are applied by the shell, not by pages: UIKit through container trait overrides (`DemoSettingsTraits`), SwiftUI through `DemoSettingsModifier`, Android through the activity configuration. The theme is applied at window or Activity level (C-42, see [architecture.md](architecture.md)).
- iOS demo projects use folder-synchronized groups: never edit `project.pbxproj` to add a file.
